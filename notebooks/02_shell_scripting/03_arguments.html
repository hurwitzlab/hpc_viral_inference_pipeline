Getting data into your script: Arguments

Arguments are inputs provided to a command or script at the time of its execution. These arguments allow users to control the behavior of the command or script and specify the data it should operate on.

Command line arguments

Command line arguments, also called positional arguments, are the simplest way to pass data to your script. They’re called “positional” because their meaning is determined by their position in the command line. Bash provides several special variables that give you access to these arguments:

  • $#: The number (think “#” == number) of arguments
  • $@: All the arguments in a single string
  • $0: The name of the script
  • $1, $2: The first argument, the second argument, etc.

These variables are automatically set by the shell when your script runs. You don’t need to declare them or initialize them—they’re always available. Let’s create a simple script to see how they work:

args.sh

$ cat -n 
#!/usr/bin/env bash

echo "Num of args    : \"$#\""
echo "String of args : \"$@\""
echo "Name of program: \"$0\""
echo "First arg      : \"$1\""
echo "Second arg     : \"$2\""

This script simply prints out the values of these special variables so you can see what’s happening. Let’s test it with different numbers of arguments:

$ ./args.sh
Num of args    : "0"
String of args : ""
Name of program: "./args.sh"
First arg      : ""
Second arg     : ""

When we run the script with no arguments, \(# is 0 and the argument variables are empty strings. This is important to know because if your script expects arguments, you'll need to check for this case. ```bash\) ./args.sh foo Num of args : “1” String of args : “foo” Name of program: “./args.sh” First arg : “foo” Second arg : “”

With one argument, $1 contains "foo" but $2 is still empty. Notice that accessing an argument that wasn't provided doesn't cause an error—it just gives you an empty string.
```bash
$ ./args.sh foo bar
Num of args    : "2"
String of args : "foo bar"
Name of program: "./args.sh"
First arg      : "foo"
Second arg     : "bar"

Now both $1 and $2 are populated. The $@ variable contains both arguments separated by a space, which is useful when you want to pass all arguments to another command.

Here’s a practical example that actually uses an argument to do something useful:

hello3.sh

#!/usr/bin/env bash

echo "Hello, $1!"

This script takes whatever you pass as the first argument and includes it in the greeting:

$ ./hello3.sh Captain
Hello, Captain!

This pattern of using $1, $2, etc. works well for simple scripts with just a few arguments. But as your scripts grow more complex, you’ll quickly find that managing many positional arguments becomes unwieldy. What if the user forgets an argument? What if they put them in the wrong order? We’ll address these issues in the following sections.

Providing default argument values

In the real world, not every user will provide every argument your script could use. Rather than forcing users to always specify every single value, you can provide sensible defaults for optional arguments. This makes your scripts much friendlier to use—users only need to specify the values that differ from the common case.

Bash provides parameter expansion syntax for this purpose. The most common form is ${variable:-default}, which means “use the value of variable if it’s set and not empty, otherwise use this default value.” This is non-destructive—it doesn’t actually change the variable, it just provides a fallback value for this one use.

Let’s see this in action with a greeting script that defaults to “World” if no name is provided:

greet_default.sh

#!/usr/bin/env bash

NAME=${1:-"World"}
echo "Hello, $NAME!"

Now the script works whether or not the user provides a name:

$ ./greet_default.sh
Hello, World!
$ ./greet_default.sh Alice
Hello, Alice!

This is much better than the previous version that would print “Hello, !” if no argument was given. The user experience is improved because the script does something reasonable by default.

There’s a related syntax, ${variable:=default}, which not only provides a default but also assigns it to the variable. This is useful when you want to ensure the variable has a value for later use in the script:

#!/usr/bin/env bash

: ${OUTPUT_DIR:="./output"}
echo "Output directory: $OUTPUT_DIR"

The : command is a no-op (it does nothing), but it forces bash to evaluate the parameter expansion. This idiom is commonly used at the top of scripts to set up default values for variables that might come from arguments or environment variables.

You can also use conditional logic to provide defaults, which gives you more flexibility:

bash#!/usr/bin/env bash

if [ -z "$1" ]; then
    NAME="World"
else
    NAME="$1"
fi

echo "Hello, $NAME!"

This approach is more verbose but sometimes clearer, especially when the default value needs to be computed or when you want to provide different messages based on whether the argument was provided.

Environmental arguments

Environment variables provide another channel for passing information to your scripts. Unlike command line arguments, which are explicitly provided each time you run the script, environment variables are set in the shell environment and persist across multiple commands. They’re particularly useful for configuration that applies to many different programs or scripts in a session.

Your shell already sets many environment variables automatically. Common ones include $USER (your username), $HOME (your home directory), and $PATH (where the shell looks for commands). Let’s see how to access these in a script:

env_example.sh

#!/usr/bin/env bash

echo "User: $USER"
echo "Home: $HOME"
echo "Path: $PATH"
echo "Custom var: $MY_VAR"

The syntax for accessing environment variables is identical to accessing regular shell variables—just use the dollar sign followed by the variable name:

$ export MY_VAR="custom_value"
$ ./env_example.sh
User: your_username
Home: /home/your_username
Path: /usr/local/bin:/usr/bin:/bin
Custom var: custom_value
Important

The export command makes a variable available to child processes (like your script). Without export, the variable would only exist in the current shell and wouldn’t be visible to the script.

You can also set environment variables for just a single command execution without affecting your shell environment:

$ MY_VAR="temporary_value" ./env_example.sh

This syntax is useful for one-off runs or when testing different configurations. The variable is only set for the duration of that one command.

Environment variables are particularly powerful when combined with default values. This pattern allows scripts to be configured through the environment while still working with sensible defaults:

deploy.sh

#!/usr/bin/env bash

ENVIRONMENT=${ENVIRONMENT:-"development"}
PORT=${PORT:-8080}
DEBUG=${DEBUG:-false}

echo "Deploying to: $ENVIRONMENT"
echo "Port: $PORT"
echo "Debug mode: $DEBUG"

Now you can run the script with defaults, or configure it through environment variables:

$ ./deploy.sh
Deploying to: development
Port: 8080
Debug mode: false

$ ENVIRONMENT=production PORT=3000 ./deploy.sh
Deploying to: production
Port: 3000
Debug mode: false

This approach is common in modern application deployment, where environment variables configure things like database connections, API keys, and feature flags. It follows the twelve-factor app methodology, which recommends storing configuration in the environment rather than in code.

Required and optional arguments

As your scripts become more sophisticated, you’ll need to distinguish between required arguments (without which the script cannot function) and optional arguments (which have reasonable defaults). Good scripts validate their inputs early and provide clear error messages when something is wrong. This prevents cryptic errors later and helps users understand how to use your script correctly. The simplest validation is checking whether a required argument was provided. We can use the -z test, which returns true if a string is empty:

#!/usr/bin/env bash

SOURCE=$1
DEST=$2

if [ -z "$SOURCE" ] || [ -z "$DEST" ]; then
    echo "Error: Missing required arguments"
    echo "Usage: $0 <source> <destination>"
    exit 1
fi

if [ ! -f "$SOURCE" ]; then
    echo "Error: Source file '$SOURCE' does not exist"
    exit 1
fi

cp "$SOURCE" "$DEST"
echo "File copied successfully"

This script validates both that the arguments are provided and that the source file actually exists before attempting the copy. The exit 1 command terminates the script with a non-zero exit code, which by convention indicates an error.

Testing this script:

$ ./copy_file.sh
Error: Missing required arguments
Usage: ./copy_file.sh <source> <destination>

$ ./copy_file.sh file.txt backup.txt
File copied successfully

Notice how the error message includes a usage statement showing the correct syntax. This is crucial for usability—when a script fails, users need to know what they did wrong and how to fix it. Including $0 (the script name) in the usage message makes it accurate even if the script is renamed or called from a different location.

You can mix required and optional arguments by checking for the required ones first:

#!/usr/bin/env bash

INPUT=$1
OUTPUT=${2:-"output.txt"}
VERBOSE=${3:-false}

if [ -z "$INPUT" ]; then
    echo "Error: Input file is required"
    exit 1
fi

echo "Processing $INPUT -> $OUTPUT"
[ "$VERBOSE" = "true" ] && echo "Verbose mode enabled"

This pattern works, but it has a significant limitation: all arguments must be provided in the exact order the script expects. If you want verbose mode but the default output file, you’d have to write ./script.sh input.txt output.txt true, explicitly providing the default. This quickly becomes tedious and error-prone, which is why we need named arguments for anything beyond the simplest scripts.


Named Arguments To The Rescue

By this point, you may be thinking that scripts are getting awfully complicated just to allow for a combination of required and optional arguments all given in a particular order. You can manage with 1-3 positional arguments, but after that, we really need to have named arguments and/or flags to indicate how we want to run the program.

Named arguments fundamentally change how users interact with your script. Instead of memorizing the correct order of arguments, users specify what each value represents with a flag. A named argument might be -f mouse.fa to indicate the value for the -f flag (probably “file”) is mouse.fa, whereas a simple flag like -v might be a yes/no (“Boolean”) indicator that we do or do not want “verbose” mode. You’ve encountered these with programs like ls -l to indicate you want the “long” directory listing or ps -u $USER to indicate the value for -u is the $USER variable.

The best thing about named arguments is that they can be provided in any order:

$ ./named.sh -n Patch -g "Good Boy"
Good Boy, Patch!

$ ./named.sh -g "Good Boy" -n Patch
Good Boy, Patch!

Both invocations produce the same result because the flags tell the script what each value means. Some flags may have values (like -n Patch), some may be simple boolean flags (like -v for verbose), and you can easily provide good defaults to make it easy for the user to provide the bare minimum information to run your program. This is the standard pattern used by professional Unix tools, and users will find your scripts immediately familiar if you follow these conventions.

Using getopts for Named Arguments

The getopts built-in command is bash’s standard tool for parsing named arguments. It handles all the tedious work of parsing flags, extracting their values, and detecting errors. Here’s a complete example that demonstrates the key patterns:

named.sh

#!/usr/bin/env bash

set -u

GREETING=""
NAME="Stranger"
EXCITED=0

function USAGE() {
    printf "Usage:\n  %s -g GREETING [-e] [-n NAME]\n\n" $(basename $0)
    echo "Required arguments:"
    echo " -g GREETING"
    echo
    echo "Options:"
    echo " -n NAME ($NAME)"
    echo " -e Print exclamation mark"
    exit ${1:-0}
}

[[ $# -eq 0 ]] && USAGE 1

while getopts :g:n:eh OPT; do
  case $OPT in
    h)
      USAGE
      ;;
    e)
      EXCITED=1
      ;;
    g)
      GREETING="$OPTARG"
      ;;
    n)
      NAME="$OPTARG"
      ;;
    :)
      echo "Error: Option -$OPTARG requires an argument."
      exit 1
      ;;
    \?)
      echo "Error: Invalid option: -${OPTARG:-""}"
      exit 1
  esac
done

[[ -z "$GREETING" ]] && USAGE 1
PUNCTUATION="."
[[ $EXCITED -ne 0 ]] && PUNCTUATION="!"

echo "$GREETING, $NAME$PUNCTUATION"

Let’s break down what’s happening here. The set -u at the top makes bash exit if we try to use an undefined variable, which catches typos and logic errors. The USAGE function prints help text and exits with a status code (defaulting to 0 for success). Using a function for this is good practice because we can call it from multiple places. The line [[ $# -eq 0 ]] && USAGE 1 checks if no arguments were provided and shows usage if so. This is a common pattern—if someone runs your script with no arguments at all, they probably want to know how to use it. The real work happens in the while getopts :g:n:eh OPT; do loop. Let’s understand that option string :g:n:eh:

The leading : enables silent error reporting mode (we’ll handle errors ourselves) - g: means -g requires an argument (the colon indicates a value is expected) - n: means -n requires an argument - e: means -e is a boolean flag (no colon, no value) - h: means -h is a boolean flag for help

The case statement handles each option. When getopts finds an option that takes a value, it puts that value in the special variable $OPTARG. For boolean flags, we just set a variable to indicate the flag was present. The special cases :) and \?) handle errors—when an option is missing its required argument, or when an unknown option is provided.

When run without arguments or with the -h flag, it produces a help message:

$ ./named.sh
Usage:
  named.sh -g GREETING [-e] [-n NAME]

Required arguments:
 -g GREETING

Options:
 -n NAME (Stranger)
 -e Print exclamation mark

The script just got much longer, but it’s also much more flexible and user-friendly. This template can serve as the foundation for many different shell scripts. Both the h and e arguments are simple flags with no values:

$ ./named.sh -n Patch -g "Good Boy"
Good Boy, Patch.

$ ./named.sh -n Patch -g "Good Boy" -e
Good Boy, Patch!

$ ./named.sh -g "Good Boy" -e -n Patch
Good Boy, Patch!

All three invocations with different argument orders produce the correct results. This flexibility is why named arguments are essential for any script that will be used by others or maintained over time.

Best Practices for Named Arguments

When building scripts with named arguments, follow these conventions to make them intuitive and maintainable:

  • Use meaningful single-letter options: Common conventions include -i for input, -o for output, -v for verbose, -f for file or format, -h for help. Users familiar with Unix tools will immediately understand these without reading documentation.
  • Always provide a help option (-h) that displays usage information. Users should never have to read your source code to figure out how to use your script. The help message should include the basic syntax, explain required vs optional arguments, show default values, and ideally provide one or two examples.
  • Show default values in your usage message so users know what happens if they don’t specify an option. This is why the example above shows NAME (Stranger) —it tells users that if they don’t provide -n, the name will be “Stranger.”
  • Validate all inputs after parsing the options. Check that required arguments were provided, that files exist, that numeric values are in valid ranges, and that enum-like options are from the allowed set. Fail fast with clear error messages.
  • Set sensible defaults so users only need to specify what differs from the common case. If 90% of the time your script processes CSV files, make CSV the default format so users only need to specify -f json when they want something different.
  • Exit with appropriate status codes: Use exit 0 for success and exit 1 (or other non-zero values) for various error conditions. This allows your script to be used in pipelines and automated systems that check exit codes.


Reading a configuration file

Configuration files provide another layer of flexibility beyond command-line arguments and environment variables. They’re particularly useful for complex applications with many settings, for configurations that should persist across multiple runs, or when you want to maintain different configurations for different environments (development, staging, production).

A configuration file is typically a simple text file with variable assignments. The beauty of bash is that you can directly source these files to load the variables into your script:

bash# Application configuration
APP_NAME="MyApp"
APP_VERSION="1.0.0"
LOG_LEVEL="INFO"
DATABASE_HOST="localhost"
DATABASE_PORT=5432

The simplest way to use a configuration file is with the source command, which reads and executes the file in the current shell context:

read_config.sh

#!/usr/bin/env bash

CONFIG_FILE=${1:-"config.conf"}

if [ ! -f "$CONFIG_FILE" ]; then
    echo "Error: Configuration file '$CONFIG_FILE' not found"
    exit 1
fi

source "$CONFIG_FILE"

echo "Application: $APP_NAME v$APP_VERSION"
echo "Log Level: $LOG_LEVEL"
echo "Database: $DATABASE_HOST:$DATABASE_PORT"

This works beautifully because the configuration file is just valid bash syntax. When you source it, all the variable assignments become available to your script. You can even include comments in the config file (lines starting with #) to document what each setting does.

For production scripts, you’ll want to be more robust about configuration handling. Here’s a pattern that combines defaults, config files, and validation: app_with_config.sh

#!/usr/bin/env bash

CONFIG_FILE="app.conf"

# Set defaults
PORT=${PORT:-8080}
WORKERS=${WORKERS:-4}
LOG_LEVEL=${LOG_LEVEL:-"INFO"}

# Load config file if it exists
if [ -f "$CONFIG_FILE" ]; then
    echo "Loading configuration from $CONFIG_FILE"
    source "$CONFIG_FILE"
else
    echo "No config file found, using defaults"
fi

# Validate configuration
if [ "$PORT" -lt 1024 ] || [ "$PORT" -gt 65535 ]; then
    echo "Error: Invalid port number $PORT"
    exit 1
fi

echo "Starting application..."
echo "Port: $PORT"
echo "Workers: $WORKERS"
echo "Log Level: $LOG_LEVEL"

This script demonstrates a layered configuration approach: first set defaults in the script, then load values from a config file if present (which can override the defaults), then validate that the final values make sense. This gives users flexibility in how they configure the application while ensuring it always has valid values.

You can test this with an app.conf file:

# app.conf
PORT=3000
WORKERS=8
LOG_LEVEL="DEBUG"
Running the script:
bash$ ./app_with_config.sh
Loading configuration from app.conf
Starting application...
Port: 3000
Workers: 8
Log Level: DEBUG

This approach scales well. You can maintain different configuration files for different environments (dev.conf, prod.conf) and simply pass the appropriate file as an argument or environment variable. The combination of config files, environment variables, defaults, and command-line arguments gives users maximum flexibility in how they configure your scripts.

Key Takeaways

After completing this training, you should understand these fundamental concepts about shell script arguments:

1. Positional arguments are simple but limited: The variables $1, $2, $3, etc. provide the easiest way to accept input, but they require users to remember the exact order of arguments. They work well for scripts with 1-3 arguments but become unwieldy beyond that. Always check if required positional arguments are provided using [ -z "$1" ] or similar tests.

2. Default values make scripts user-friendly: Using the syntax ${variable:-default} allows your scripts to work out of the box while still being configurable. This dramatically improves the user experience because people only need to specify values that differ from the common case. Every optional argument should have a sensible default.

3. Environment variables enable persistent configuration: Unlike command-line arguments that must be provided each time, environment variables persist across multiple commands in a session. They’re ideal for settings like database connections, API keys, or feature flags. The combination of environment variables with defaults (VARIABLE=${VARIABLE:-default}) gives users flexibility in how they configure your scripts.

4. Named arguments are essential for complex scripts: The getopts command lets you parse flags like -i input.txt or -v for verbose mode. Named arguments can be provided in any order, making your scripts much more intuitive to use. Once you have more than 3 arguments or a mix of required and optional parameters, named arguments become necessary.

5. Validation and error messages are not optional: Professional scripts always validate their inputs and provide clear, helpful error messages when something is wrong. Check that required arguments are provided, that files exist, that numeric values are in valid ranges. A good error message should explain what went wrong and show the correct usage syntax.

6. Configuration files separate settings from code: For complex applications with many settings, configuration files let users maintain different configurations (development, staging, production) without modifying the script itself. Using source config.conf makes loading configuration trivial in bash.

7. Layer your configuration for maximum flexibility: The most robust scripts combine all these approaches: defaults in the script, values from a config file, environment variables, and command-line arguments. Each layer can override the previous one, giving users control at multiple levels while ensuring the script always has valid values.

Exercise 1: File Backup Script with Defaults

Create a script called backup.sh that backs up files with the following requirements:

  • Takes a source file as the first positional argument (required)
  • Takes a backup directory as the second positional argument (optional, defaults to ./backups)
  • Takes a timestamp flag as the third argument (optional, defaults to false)
  • If the timestamp flag is “true”, append the current date/time to the backup filename
  • Create the backup directory if it doesn’t exist
  • Validate that the source file exists before attempting to back it up
  • Print a success message showing where the backup was created

Example usage:

$ ./backup.sh important.txt
Backed up important.txt to ./backups/important.txt

$ ./backup.sh important.txt /tmp/backups true
Backed up important.txt to /tmp/backups/important_20231208_143022.txt

Hints: Use mkdir -p to create directories, date +%Y%m%d_%H%M%S for timestamps, and parameter expansion for defaults.
