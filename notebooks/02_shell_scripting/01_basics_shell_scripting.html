Statements

In programming, a statement is like a sentence—it’s a complete instruction that tells the computer to do something. In bash, each command you write is a statement.

How Bash Knows Where One Statement Ends

Bash uses two ways to mark the end of a statement:

  1. Newline (pressing Enter): The most common way
  2. Semicolon (;): Separates multiple statements on one line

Examples

One statement per line (most common and readable):

$ echo "Hi"
Hi
$ echo "Hello"
Hello

Multiple statements on one line (using semicolons):

$ echo "Hi"; echo "Hello"
Hi
Hello

Both approaches work the same way, but separate lines are usually easier to read.

Breaking Long Commands Across Multiple Lines

Sometimes a command gets too long to fit comfortably on one line. You can split it using a backslash \ at the end of the line:

$ echo "This is a very long message" \
> "that continues on the next line"
This is a very long message that continues on the next line

The \ tells bash: “This statement isn’t finished yet—continue on the next line.”

TipWhen to Use Each Style
  • Newlines (pressing Enter): Best for normal scripts—clearest and easiest to read
  • Semicolons: Useful for quick one-liners in the terminal or compact scripts
  • Backslash continuation: Helpful for long commands with many options or arguments
# Good: Easy to read
echo "Hello"
echo "World"

# Also valid: Compact one-liner
echo "Hello"; echo "World"

# Good for long commands
docker run --name mycontainer \
  --volume /data:/data \
  --env KEY=value \
  myimage:latest
NoteThe > Prompt

When you use \ to continue a line, you’ll see a > prompt. This means bash is waiting for you to finish the statement. Just keep typing and press Enter when done.

Comments

Every programming language needs a way to include notes in your code that won’t be executed. In bash and many Unix-style languages, we use the # (hash or pound) symbol for comments. Everything after # on that line is ignored by the program.

Why use comments?

  1. Explain your code: Help others (and future you!) understand what’s happening
  2. Disable code temporarily: Test different approaches without deleting code

Here’s an example in bash:

#!/usr/bin/env bash

# This script greets the user
NAME="Alice"

echo "Hello, $NAME"  # Print greeting to screen

# Temporarily disabled - testing without this line
# echo "Goodbye, $NAME"
Note

In bash, comments start with #. Other languages use different symbols:

  • JavaScript, Java, Rust: //
  • Python, Ruby, Perl: #

Shebang: Telling the System How to Run Your Script

When you create a script file, your system needs to know which program should interpret it. That’s where the shebang line comes in.

What’s a Shebang?

The shebang is the first line of a script that starts with #! followed by the path to the interpreter. It looks like a comment, but it’s actually a special instruction to your operating system.

Why Do We Need It?

Let’s see what happens without a shebang:

# Create a Python script without a shebang
$ echo 'print("Hello, World")' > hello.py
$ chmod +x hello.py
$ ./hello.py
./hello.py: line 1: syntax error near unexpected token `"Hello, World"'

What went wrong? When you run ./hello.py, bash tries to interpret it as a bash script, but print() isn’t valid bash syntax.

The solution: Add a shebang to tell the system “use Python to run this”:

$ cat hello.py
#!/usr/bin/env python3
print("Hello, World")

$ ./hello.py
Hello, World

Now it works! The system sees the shebang and knows to use Python.

Two Ways to Write Shebangs

Option 1: Direct path

#!/bin/bash
#!/usr/bin/python3

Points directly to the interpreter’s location.

Option 2: Using env (recommended)

#!/usr/bin/env bash
#!/usr/bin/env python3
TipWhy use #!/usr/bin/env?

Using env makes your script more portable. Instead of hardcoding a specific path like /usr/local/bin/python3, env finds the first matching program in your $PATH.

This means your script will work on different systems where Python might be installed in different locations.

Running Scripts: Two Methods

Method 1: Call the interpreter explicitly (no shebang needed, no execute permission needed)

$ bash hello.sh
Hello, World

$ python3 hello.py
Hello, World

Method 2: Make it executable (requires shebang and execute permission)

$ chmod +x hello.sh
$ ./hello.sh
Hello, World

The second method is cleaner and more common, but both work!

WarningRemember
  • The shebang must be the first line of your file
  • No spaces after #!
  • The file must be executable (chmod +x) to run with ./

Variables: Storing and Using Information

Variables let you store information and reuse it throughout your script. Think of a variable as a labeled box where you can put data.

Creating Your First Variable Script

Let’s create a script that greets different people:

$ cat -n hello2.sh
     1    #!/usr/bin/env bash
     2
     3    NAME="Alex"
     4    echo "Hello, $NAME"
     5    
     6    NAME="River"
     7    echo "Hello, $NAME"

$ ./hello2.sh
Hello, Alex
Hello, River

How Variables Work

Creating a variable:

NAME="Alex"          # No $ when assigning

Using a variable:

echo "Hello, $NAME"  # Use $ to get the value

The Spacing Rule: Critical!

Bash is very strict about spaces around the = sign:

# ✓ CORRECT: No spaces around =
NAME="Casey"
echo "Hello, $NAME"
Hello, Casey

# ✗ WRONG: Spaces around =
NAME = "Casey"
-bash: NAME: command not found

echo "Hello, $NAME"
Hello,

What happened? Bash thought NAME was a command, not a variable assignment!

ImportantKey Rules for Variables
  1. No $ when assigning: NAME="Alex"
  2. Use $ when accessing: echo $NAME
  3. No spaces around =: Spaces will cause errors!

Variables Can Change

You can update a variable’s value at any time:

#!/usr/bin/env bash

GREETING="Hello"
echo "$GREETING, Alex"      # Hello, Alex

GREETING="Goodbye"
echo "$GREETING, Alex"      # Goodbye, Alex

Naming Variables: Best Practices

Case sensitivity matters:

name="Jordan"
Name="Taylor"
NAME="Quinn"

echo $name    # Jordan
echo $Name    # Taylor
echo $NAME    # Quinn

These are three completely different variables!

TipConvention:

Use uppercase for your variables

NAME="Alex"
GREETING="Hello"
COUNT=5
WarningDon’t Overwrite System Variables!

Some variable names are reserved for the system. Never use these names:

  • PATH - Where the system finds programs
  • HOME - Your home directory location
  • USER - Your username
  • SHELL - Your current shell
# ✗ DANGEROUS - Don't do this!
PATH="mydata"
echo $PATH
# Now bash can't find any commands!

# ✓ SAFE - Use a different name
DATA_PATH="mydata"
echo $DATA_PATH

If you accidentally overwrite PATH, close your terminal and start fresh.

Quoting Variables: When Does It Matter?

You’ll often see variables used with quotes:

NAME="Sam"

# Both work for simple cases:
echo Hello, $NAME        # Hello, Sam
echo "Hello, $NAME"      # Hello, Sam

But quotes become important with spaces:

NAME="Sam Lee"

echo Hello, $NAME        # Could cause issues
echo "Hello, $NAME"      # Safer - keeps everything together
TipBest Practice

Get in the habit of using quotes around variables: "$NAME" instead of just $NAME. It prevents unexpected behavior when values contain spaces.

Catching Common Errors with set -u

Bash won’t warn you when you misspell a variable name—it just treats it as an empty variable. This can lead to silent bugs that are hard to find.

The Problem: Silent Typos

Watch what happens when you mistype a variable:

$ echo $HOME
/home/username

$ echo $HOEM     # Oops, typo!
                 # No output, no error!

Bash just assumes $HOEM is an empty variable and continues without complaint.

The Solution: set -u

Add set -u at the top of your scripts to catch undefined variables:

$ set -u
$ echo $HOEM
-bash: HOEM: unbound variable

Now bash alerts you to the typo!

TipAdd set -u

Always add set -u near the top of your scripts, right after the shebang. It’s not technically required, but it’s a best practice that can save you from frustrating bugs. Just like wearing a helmet while biking, it protects you when things go wrong.

WarningWhat set -u Won’t Catch

set -u only catches errors when the code actually runs. Test your scripts with different inputs to exercise all code paths!

TipPro Tip: Use ShellCheck

For even better error detection, use ShellCheck—a tool that analyzes your bash scripts for common mistakes before you even run them.

Online: Visit shellcheck.net

Key Takeaways

By completing this training, you now understand:

Core Concepts

  • Statements: Commands are separated by newlines or semicolons (;)
  • Comments: Use # to document your code or disable lines temporarily
  • Shebang: The #!/usr/bin/env bash line tells the system how to run your script
  • Variables: Store and reuse data; use NAME="value" to assign, $NAME to access
  • Error checking: Use set -u to catch undefined variables

Critical Rules to Remember

  1. No spaces around = when assigning variables: NAME="Alex" ✓ not NAME = "Alex" ✗
  2. Use $ only when accessing variables, not when assigning them
  3. Everything is case-sensitive: $NAME, $Name, and $name are different variables
  4. Never overwrite system variables like PATH, HOME, or USER
  5. Always use set -u at the top of your scripts to catch typos

Best Practices

  • Start every script with a shebang: #!/usr/bin/env bash
  • Add set -u right after the shebang
  • Use quotes around variables: "$NAME" is safer than $NAME
  • Write comments to explain complex logic
  • Use ShellCheck to validate your scripts before running them
  • Test scripts with different inputs to exercise all code paths

  1. Run the script and identify all errors
